# v9.20.0 · 钉钉助手整体重做

> 这一版把「助理」从一个**只能看内存里一堆消息**的面板，改成了
> 一个有持久化底座、有范围控制、有身份记忆、还能自己判断「我不知道」的助手。

---

## 一、为什么要重做

老实现（`app/assistant.py` 时代的助理页）有四个硬伤，用户全都撞过：

| 现象 | 真因 |
| --- | --- |
| 「AI 正在处理中，最后消息消失不见，不回复」 | 待处理消息只在 `MainWindow._asst_queue` 内存里，一重启全没；处理线程异常时也只写日志不发消息 |
| 「切换对话后记忆混乱」 | `workspace.files_dir` 读全局当前对话，助理用的却是另一个对话的目录 |
| 「群里的话不该回也回」 | 范围只有 `self / all / at_me` 三档下拉，没法细到「群聊要、但群里只回@我的」 |
| 「AI 瞎编」 | 没有任何"我不知道"的出口，模型只能硬编 |

## 二、分层结构

```
app/im/
├── store.py      持久化（会话档案 / 消息流水 / 任务 / 日志本 / 记忆 / 设置 / 标签）
├── policy.py     「回不回、怎么回」—— 范围闸门 + 模式 + 系统提示 + 拿不准哨兵
├── scheduler.py  定时主动消息（每日/每周/每月）—— 纯函数，只算"这一周期该不该发"
├── logbook.py    「谁·哪天·干什么」抽取与查询（值日、排班这类）
├── tags.py       会话全量扫描 + AI 打关系标签（纯逻辑，能力靠注入）
└── hub.py        编排：收 → 判定 → 组上下文 → 调模型 → 回 → 落盘
```

**铁律：前五个模块不碰 Qt、不碰网络，全靠注入。** 所以能拿假实现直接跑探针。
只有 `hub` 会拿着注入进来的 `llm_fn` / `send_fn` 干活，`MainWindow` 负责把真实的
模型调用和 dws 发送塞进去。

### 落盘位置

```
<工作区>/.awb/im/
├── threads.json          会话档案（名字/类型/模式/人设/规则/上下文条数/标签）
├── im_settings.json      用户在「设置」页填的全部东西
├── msgs/<会话>.jsonl     消息流水（in/out、谁说的、是不是 AI、处理状态）
├── tasks.json            定时任务
├── logbook.jsonl         日志本
├── memory.md             共享记忆（所有会话都能看到）
└── mem/<会话>.md         这个会话自己的记忆
```

老版本没有这些文件也能跑（空列表 + 默认值），**不做隐式迁移**。

## 三、「消息」页的两栏是怎么算出来的

`IMStore.rows()` 把 append-only 的 jsonl 折成界面要的数据：

1. 读每个会话的流水（本地文件，不走网络）。
2. 建三张表：
   - `status_rec[status_of]` —— 带 `status_of` 的是「某条消息的处理状态回执」；
   - `dropped` —— `status == "deleted"` 的，代表用户删掉了；
   - `free_out` —— 没有 `status_of` 的 `out` 消息（hub 直接追加的 AI 回复 / 定时消息）。
3. 每条 `in` 消息：
   - 有 `status_rec` → 按它定 `已回复 / 处理中 / 失败 / 需人工`，并把 AI 原话填进 `reply`；
   - 没有就找 `free_out` 里**时间在其之后的第一条**当回复；
   - 都没有 → `待处理`，`reply=""`。
4. 按收到时间**倒序**（最新在前）。

界面上：`status == "已回复"` 进右栏，其余全部进左栏。
所以「处理中 / 失败 / 需人工」都老老实实待在左栏 —— 这才是"还没回"的真实状态。

**删除** `hide_message()` 追加一条 `{"status": "deleted", "status_of": mid}`，
不真删文件。好处：① 不破坏 append-only；② 重启后照样不冒出来；
③ 想恢复只要删掉那一行。

## 四、范围与白名单（`policy.should_reply`）

顺序不能乱，先闸门后模式：

```
① 白名单命中（按 cid）            → 回（"白名单"）
② kind 是 p2p/dm/self 且没勾「单聊」 → 不回
③ kind 是 group 且没勾「群聊」      → 不回
④ 勾了「只在群里@我」且没被叫到     → 不回
⑤ 落到原来的 mode 判定（秘书/同事/群助手）
```

⚠ `settings=None` 时**完全走老逻辑**——老的 `probe_im_core_v920.py` 还在用三参数调用，
不能因为加了闸门就把它弄红。

**白名单按 cid 匹配。** 用户在界面上打的是名字，所以 `MainWindow._im_whitelist_add`
会先在 `threads()` 里拿名字反查 cid；查不到就照原样存下并**明确告诉用户**
「还没对上具体会话，等收到过它的消息后再加一次」—— 不假装成功。

## 五、延时回复（「我多少秒没自己回才代回」）

这是本版最容易被写错的一块。

```
消息进来
  → recv_ts = now
  → _asst_not_before[mid] = now + delay_seconds
  → 入队
_asst_pump 一旦发现队首还没到点 → QTimer 到点再叫自己，不阻塞
到点后 _asst_start：
  → 查 im_store.last_manual_out(cid)
  → 如果它 > recv_ts（这期间我本人在钉钉里回过）→ 标「已回复」并跳过，不代回
```

要让 `last_manual_out` 有数据，**必须把我本人发的消息也记进流水**。
为此 `AssistantService` 新增 `outgoing` 信号：`scan_once` 里原本被
`if scope != "self" and sender == mine: continue` 丢掉的那些消息，
现在单独抛出去，由 `MainWindow._assistant_on_outgoing` 以
`direction="out", ai=False` 落盘。

顺带的好处：AI 组上下文时终于能看到「我本人是怎么说话的」，语气才对得上
（以前流水里只有对方说的 + AI 自己回的，模型是在学自己的套话）。

### 一个必须记住的坑

`apply_cfg` 里加了：

```python
if new_scope and new_scope != old_scope:
    self.cfg["primed"] = False
    self.cfg["processed"] = []
```

否则从「只听自聊」切到「所有会话」的那一瞬间，程序会把过去几个月的聊天记录
**全当成新消息**，一条条排队回过去。这是灾难级的，必须重新"跳过历史"。

## 六、AI 拿不准 → `[[UNCERTAIN]]`

系统提示（`policy.py`）里固定写死：

```
## 拿不准的时候
如果对方问的事情在你上面的身份背景、记忆、上下文里都查不到，你也推断不出来，
就不要猜：整条回复只输出一行 `[[UNCERTAIN]]`，不要输出别的任何文字。
能推断出来（比如按常识、按上下文）就直接回答。
```

`MainWindow._asst_finish` 见到这个哨兵就：

- 用户勾了「拿不准也要回」→ 换成 `uncertain_text`（默认
  「消息已纳入收件箱，加急处理中，主人正在赶来的路上，此消息由AI代回」）发出去；
- 没勾 → 状态标 `需人工`，**留在左栏**，写一条日志「按你的设置不代回」，
  然后 `_asst_done()` 复位队列（**不发消息**，但也不能把队列卡死）。

> 为什么要哨兵而不是让模型自己说「我不知道」？因为自然语言判断不可靠 ——
> 模型可能写「我不太确定，可能是 X」，那就是在硬编。哨兵是**确定性字符串**，
> 程序能 100% 认出来。

## 七、「标签」页的扫描

`tags.scan_and_tag()`：

1. `collect()` —— 列会话（最多 40 个）、每个读最近 20 条，
   **剔掉我自己发的和 AI 自己发的**（否则会拿助手自己的套话去判关系）。
   一个会话读失败不影响其它会话，全函数**绝不抛异常**。
2. 排序：群聊在前、单聊在后，组内按最近对话时间倒序（`sort_convs`）。
3. 逐个会话问模型：`build_prompt` 要求**只输出一个 2~8 字标签，证据不足就只说"不知道"**。
4. `parse_tag` 严格解析：去标点 / 去「标签：」前缀 / 超 12 字硬截 /
   含「不知道/不确定/无法判断/未知」一律返回空串。
5. **人工标签永不覆盖**：`tag` 非空且 `tag_auto` 为 False 的会话直接跳过。

跑在独立 `QThread` 里（`MainWindow._im_tag_scan`），进度实时回显
「正在扫描 7/23：家长群」。钉钉接口有节流，所以**串行、不并发**。

## 九、已知限制

- **`scope="all"` 时每轮轮询要 N 次 dws 调用**（每个会话一次）。默认 `max_convs=15`，
  但 15 个会话 × 0.5~1 秒仍然是 8~15 秒，所以检查间隔别设太小（默认 25 秒）。
- **延时回复依赖轮询**。如果你在 `delay_seconds` 内自己回了，但那一轮轮询还没跑到，
  AI 仍可能代回一次。要彻底消除得用钉钉 Stream 回调，目前没做。
- **标签只在手动点「扫描并打标签」时更新**，不会自动重扫（避免每次开程序都刷一遍钉钉接口）。
- **删除是软删除**（`status="deleted"` 的记录），jsonl 行数会慢慢涨；
  `compact()` 到 4000 行才压缩一次。
